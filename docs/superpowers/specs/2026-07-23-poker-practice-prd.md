## 1. 产品概述

本项目是一个用于个人练习无限注德州扑克的本机 Web 应用。用户从后端预设人物目录选择 5–8 个 AI 对手进行连续现金桌练习。每个 AI 对手是独立的单回合决策 Agent，默认使用 DeepSeek；仅在 DeepSeek 欠费、传输失败、请求超时或明确返回 502/503/504 时，针对当前行动降级到 Kimi。

产品的核心价值是：

1. 提供规则正确、状态可恢复的 6–9 人无限注德州现金桌。
2. 提供多种由后端维护、打法和人物形象不同的只读 AI 预设人物。
3. 保存完整、连续、可调试的牌局与 Agent 调用审计数据。
4. 通过分街行动记录、基础统计和手动 Coach 复盘支持事后学习。

本产品不是扑克求解器或真人游戏平台。Coach 提供有来源边界的教学参考，不承诺任意场景的精确 GTO 或唯一正确答案。

## 2. 用户与使用环境

- 当前版本只有一个本地用户，不提供注册或登录；服务端仍以固定 `local-user` 的 `OwnerScope` 隔离资源，保证未来上线为多个互相独立的单人教练账户时不需要重写领域和 Agent Runtime。
- 产品始终是“每位用户独立与 AI 练习并获得 Coach 复盘”，不发展用户之间的多人牌桌。
- 前后端都在同一台电脑运行，只监听本机地址。
- 首版只提供 360–430 CSS px 的手机竖屏布局，并适配顶部和底部安全区域。
- 更宽的桌面浏览器只在页面中央承载最大 430px 宽的手机画布，不提供独立宽屏布局；横屏显示旋转提示。
- 界面仅提供简体中文；常见扑克缩写保留英文并提供中文解释。
- SQLite 和运行数据都保存在项目本地数据目录。

## 3. 技术约束

- 前端：React + Vite + TypeScript；TanStack Query 管理服务端状态，Zustand 管理页面级或跨组件的纯客户端状态，组件私有状态使用 React 内置状态。
- 后端：Node.js + Hono + TypeScript；Zod 负责边界校验，dotenv 只在后端加载环境变量，Vercel AI SDK 接入 DeepSeek 和 Kimi。
- 数据库：项目本地 SQLite，使用 Drizzle ORM + `better-sqlite3`，迁移由 Drizzle Kit 管理。
- 仓库：单仓库，使用 pnpm workspace。
- 推荐目录边界：
  - `apps/web`：React/Vite 前端。
  - `apps/server`：Hono、牌局引擎、数据与 Agent 模块。
  - `packages/contracts`：前后端共享 Zod 协议、事件 Schema 和推导类型，不共享数据库内部模型。
- 不使用 TanStack Start；它的全栈路由和服务端能力与已确认的 Hono + Vite 边界重叠。
- API Key 只从后端环境变量读取，不进入浏览器、SQLite 或日志。

## 4. 术语

- **场次（Session）**：用户组桌后开始、主动结束前的一段连续现金桌练习。
- **手牌（Hand）**：从轮转庄位和下盲开始，到底池分配结束的一手牌。
- **AI 预设人物（Agent Persona）**：由后端版本化维护、前端只读的人物外观、风格参数、人设文本和模型配置。
- **Agent 实例（Session Agent）**：从预设人物或上一场阵容快照复制、只在某一场次内存在的独立 AI 对手。
- **Coach 复盘（Coach Review）**：用户对一手已结束内部手牌发起的只读教学分析；它与牌桌玩家 Agent 隔离，不产生扑克命令。
- **审计事件（Audit Event）**：按顺序保存的命令、状态变化或外部调用结果。
- **状态快照（Snapshot）**：用于刷新或重启恢复的最新权威牌局状态。

## 5. 核心用户流程

### 5.1 选择 AI 预设人物

后端提供只读的 AI 预设人物目录。每个人物至少包含：

- 稳定的 `personaId` 和 `personaVersion`。
- 姓名、背景描述及从固定高对比度色板分配的文字头像颜色。
- 松紧度、激进度、诈唬倾向、抗压跟注倾向和风险偏好。
- 自由文本策略说明。
- DeepSeek 与 Kimi 的模型标识及非敏感模型参数。

首版至少预置八个差异化人物，包含紧弱鱼、松凶娱乐玩家、标签职业玩家、短筹码鲨鱼、跟注站、超深筹码浪人、小球常客和慢打猎手。用户只能读取和选择，不能创建、编辑、复制、删除或导入人物。预设人物不保存跨场记忆，同一场次不得重复选择同一个人物。

### 5.2 新建练习

1. 用户从预设人物目录选择 5–8 个不同人物，或沿用上一场满足 6–9 人限制的阵容配置快照；两种方式都不复制上一场记忆。
2. 系统为本场创建全新的 Agent 实例，并固化人物标识、版本和完整配置快照。
3. 用户调整入座顺序或随机排座。
4. 所有座位以 2,000 筹码入桌。
5. 阵容在本场开始后锁定；换人需要结束本场并新建场次。

### 5.3 进行牌局

1. 服务端轮转庄位并发牌。
2. 玩家和 AI 按合法顺序行动。
3. 每个合法行动成功持久化后，前端才展示新状态。
4. AI 调用失败且无法降级或纠错时，整桌暂停，不使用本地策略代打。
5. 每手结束后停留在结果摘要。
6. 用户可以补码、继续下一手或结束本场。

### 5.4 复盘与统计

用户可以：

- 按场次和手牌查看翻前、翻牌、转牌、河牌及摊牌的顺序行动。
- 默认查看用户底牌和进入摊牌的未弃牌玩家底牌；已弃牌或直接获胜玩家的底牌默认隐藏，手牌结束后可以显式审计揭示全部底牌。
- 查看关联的 Agent 调用链。
- 按日期、场次、用户逻辑位置、单手盈亏、标准起手牌类别和 AI 人物配置快照筛选。起手牌类别使用 `AA`、`AKs`、`AKo` 等标准表示，不区分具体花色。
- 查看自己和 AI 的基础统计。
- 在一手结束后手动请求 Coach 复盘；系统按用户的每个实际决策点展示策略基准、局面约束、对手证据和独立的事后解释。
- 查看策略数据来源、版本和适用状态；未覆盖、非 100BB 仅可参考或样本不足时必须明确提示。

## 6. 游戏规则

### 6.1 牌桌与盲注

- 牌桌固定支持九席：用户固定占一席，AI 占 5–8 席。
- 实际玩家数限定为 6–9；不创建或继续少于 6 人的场次。
- 小盲 10，大盲 20。
- 无限注德州扑克。
- 无前注、straddle 和抽水。
- 初始及单次买入上限为 2,000，即 100BB。

### 6.2 连续现金桌

- 筹码跨手保留。
- 用户可以在两手之间补至最多 2,000。
- AI 在一手结算后即使筹码归零也不立即买入；只有用户成功执行“开始下一手”时，系统才为每个余额为 0 的 AI 自动重新买入 2,000，并在同一事务内继续发下一手。
- 用户直接结束场次时不为归零 AI 买入；“开始下一手”失败或事务回滚时也不得留下买入记录或筹码变化。
- 用户归零后必须选择重新买入 2,000 或结束场次。
- 用户余额为 0 且尚未重新买入时，“开始下一手”命令在任何 AI 自动买入前被拒绝。
- 余额大于 0 时可以继续下一手，不设置 500 筹码或其他强制补码门槛。
- 场次不限制手数和时长，由用户主动结束。
- 一手进行中不可换人、补码或结束场次。

### 6.3 行动与结算

必须支持：

- 过牌、跟注、下注、加注、弃牌和全下。
- 最小下注、最小加注及不足额全下对行动重开的正确处理。
- 多个不足额全下的累计增量达到一次完整加注量时，针对再次面对至少完整加注量的已行动玩家重新开放加注；最小再加注额仍使用本轮最后一次完整下注或加注增量。
- 短码下盲只投入剩余筹码，但名义盲注和翻前完整下注基准仍为 10/20。
- 无法被任何玩家匹配的超额投入在构建底池前返还，并生成独立审计事件。
- 主池、多层边池、平分池和奇数筹码。
- 庄位和盲位轮转。
- 6–9 人桌的按钮、大小盲、翻前和翻后行动顺序。
- 全部标准牌型、踢脚、轮子顺子、公共牌成牌和平局。
- 仍有至少两名未弃牌玩家但已经无法继续形成有效下注时，一次性发完剩余公共牌并摊牌；每个尚未发出的街道仍照常先 burn 一张。只剩一名未弃牌玩家时立即结算，不再发牌。

玩家行动提交后不可撤销，不允许用同一发牌重开当前手牌。

### 6.4 牌张资源

- 唯一静态资源目录是 `apps/web/public/poker/`，浏览器通过 `/poker/<filename>` 访问其中完整 52 张牌、牌背和两张 Joker。
- 首版只使用 52 张标准牌和牌背。
- `joker_black.png` 与 `joker_red.png` 不进入牌堆。
- 文件名作为花色和点数识别来源。

## 7. AI 对手需求

### 7.1 独立 Agent

- 每个 AI 座位是独立的单回合决策 Agent。
- Agent 只在轮到自己行动时运行一次“安全观察 → 确定性预处理 → 有界候选选择 → 校验 → 命令提交”流程。
- Agent 不后台运行、不自由调用工具、不互相通信、不生成牌桌台词。
- 模型工具集合为空；数学、合法边界、策略候选、人物偏离和对手证据在模型调用前由 Player Runtime 的固定流水线完成。
- 模型只返回 `candidateActionId`，不能自由生成动作或金额。
- 每场结束后销毁可运行的 Agent 实例，不把记忆带入新场次；本场配置和记忆版本作为只读审计快照保留到整场被删除。

### 7.2 信息隔离

Agent 只能看到：

- 自己的底牌。
- 公共牌和公开行动。
- 所有可见筹码、位置和底池。
- 当前合法行动及金额边界。
- 该角色本场的有界结构化记忆。

Agent 不得看到其他玩家未公开的底牌、未来牌张、完整牌堆或其他 Agent 的私有记忆。

### 7.3 供应商路由

DeepSeek Key 是开场必需配置。Kimi Key 缺失时允许开场，但必须明确提示自动降级不可用；如果之后确实需要降级，牌局暂停。

每次 AI 行动：

1. 优先请求 DeepSeek。
2. DeepSeek 返回结构或扑克规则错误时，仅在 DeepSeek 内最多纠错两次。
3. DeepSeek 欠费、传输失败、超过当前配置的超时时间，或明确返回 502/503/504 时，使用相同的供应商无关上下文降级到 Kimi。
4. Kimi 同样执行结构与扑克规则校验，并允许最多两次纠错。
5. Kimi 仍失败时暂停整桌。
6. 下一次行动重新优先请求 DeepSeek，不保持降级状态。

如果 DeepSeek 的纠错请求发生允许降级的故障，Kimi 使用原始 `PlayerDecisionPacket` 重新开始全新决策，不接收 DeepSeek 的错误响应或纠错历史。DeepSeek 两次纠错都返回但内容仍非法时直接暂停，不切换 Kimi。

普通 500、429、鉴权或配置错误、Schema 错误、非法扑克动作及合法但策略较差的行动不触发降级。

### 7.4 调试与审计

每次调用保存：

- 角色、手牌、行动位、状态版本和请求标识。
- 服务商、模型和路由原因。
- 脱敏请求、最终原始输出和归一化结果。
- Schema 与扑克规则校验结果。
- 自动纠错链。
- 延迟、Token 用量及错误分类。

不保存或展示供应商隐藏推理、`reasoning_content` 或思维链。

调试视图从牌桌右侧 AI 入口或手牌详情进入。暂停时可查看完整调用链并手动重试。

### 7.5 Coach Agent

- Coach 只接受应用内已结束手牌，由用户在手牌详情中手动请求；不监听手牌结束事件自动运行，也不在牌局进行中提示。
- Coach 的目标是教学，不是代打。它输出结构化只读报告，不生成或提交扑克命令，不修改扑克状态、筹码、`stateVersion` 或 `eventSeq`。
- 每个用户决策点先以当时可见信息完成过程评价，再以完整底牌和实际后续公共牌补充事后解释。事后信息不得反向改写过程评价。
- 每个决策必须分别展示策略基准、局面约束和对手证据；任何一层不支持或证据不足时必须诚实标明。
- Coach 使用服务端固定编排的确定性工具和版本化策略数据，不允许模型自由跳过必需计算或开放式调用任意工具。
- 每个用户决策的标签、严重度、基准对比和 EV 可用状态先由确定性分类器生成并冻结；LLM 只负责解释，不能重新分类或自行估算 EV。
- “动作执行频率”和“下注尺度”必须使用独立字段和明确文字。例如动作频率 75%、下注尺度 33% 底池不得简写为“下注 75%”。
- 首版策略范围为 6–9 人桌的版本化 100BB 翻前参考，以及明确列入覆盖清单的少量单挑翻牌持续下注场景；其他场景返回不支持或仅供参考。
- 长期打法标签、情绪识别和用户漏洞画像不进入首版。

详细信息边界、工具契约、两阶段模型隔离、输出 Schema 和验收要求以 [Coach Agent 专项设计](./2026-07-26-poker-coach-agent-design.md) 为唯一事实源。

## 8. 前端功能需求

首版页面：

- 训练首页。
- 组桌页。
- 牌桌页。
- 当前手与历史手牌详情页。
- 已结束手牌的 Coach 复盘视图。
- 历史页。
- 统计页。
- 设置页。
- 牌桌、AI 状态和手牌详情共用的调试视图。

普通页面使用顶部标题栏、纵向内容和“训练、历史、统计”底部主导航。进入对局后隐藏底部主导航，使用已确认的手机竖屏沉浸式牌桌：

- 纵向大椭圆牌桌占据主屏，用户固定在底部中央，其他 5–8 个座位按人数映射到九席预设位置。
- 顶部场次栏展示返回、盲注、手数、当前阶段和连接状态。
- 右侧悬浮工具栏提供本手流程、AI 状态和本场历史入口，不常驻动作时间线。
- 本手与历史手牌动作流程使用独立全屏页，按翻前、翻牌、转牌、河牌和摊牌分组；返回牌桌时读取最新快照，不还原动画牌局。
- 底部玩家操作区固定在安全区域上方。
- 座位只显示彩色文字头像、姓名、位置、筹码和当前状态，不显示风格标签或 HUD。
- 使用基本的发牌、下注和筹码变化动画，不使用音效。

下注操作提供：

- 弃牌。
- 过牌或跟注。
- 下注或加注。
- 最小加注、1/2 池、2/3 池、满池和全下快捷项。
- 精确金额输入，不提供滑杆。

底池比例快捷金额由牌局引擎按合法动作生成并裁剪到金额边界，前端不得自行实现下注公式。

AI 人物目录由后端只读提供。组桌页只允许选择 5–8 个不同预设人物、调整入座顺序、沿用符合当前人数限制的上一场阵容并确认开场；不提供人物创建、编辑、复制、删除或导入入口。

已结束手牌详情提供“请求教练复盘”入口。前端按严格结构化协议展示请求状态、逐决策四部分分析、策略来源与匹配状态，并可根据服务端 `rangeChartSpec` 渲染 13×13 翻前范围矩阵；前端不得自行计算策略、SPR、底池赔率或逻辑位置。

## 9. 日志、复盘与统计

### 9.1 完整审计数据

系统保存：

- 全部玩家底牌。
- 完整洗牌结果和 burn card。
- 每个命令、合法动作集合及状态版本。
- 场次内统一排序的扑克和 Agent 运行事件。
- 每次筹码和底池变化。
- Agent 请求、响应、纠错、降级和失败。
- 最终牌型、底池分配和净输赢。

完整隐藏信息只保存在 SQLite，用于应用内审计、调试和可控揭示。首版不提供任何数据或手牌导出功能。

### 9.2 手牌历史

不提供动画式牌局重放。单手详情按街道展示：

- 行动者、位置、动作和投入额。
- 行动后的筹码和底池。
- 公共牌和摊牌结果。
- 未跟注投入返还。
- 各底池的赢家和分配。

### 9.3 基础统计

使用固定统计口径：

- 手牌数：获发底牌的手数。
- 净盈亏：单手为结束筹码减开始筹码；场次为最终筹码减全部买入与补码总额。
- VPIP：翻前自愿跟注、下注、加注或全下的手数除以总手数；强制盲注不计入自愿投入。
- PFR：翻前至少进行一次加注或再加注的手数除以总手数。
- 3-bet：面对翻前首次加注且拥有合法再加注机会时，实际首次再加注次数除以 3-bet 机会数。
- 摊牌率 WTSD：进入摊牌的手数除以看到翻牌的手数。
- 摊牌胜率 W$SD：在摊牌中获得任意底池份额的手数除以进入摊牌的手数；平分池计为获得底池。

统计覆盖用户和 AI，可按场次、日期、逻辑位置及 AI 人物配置快照筛选。每个百分比同时展示中文定义、分子和分母；分母为 0 时显示“—”，不得伪装为 0%。

### 9.4 数据删除

- 只允许永久删除已经结束的整场数据，不允许只删除单手；删除时同步移除场次快照、命令账本、全部事件、玩家 Agent 调用与记忆版本、Coach 报告与调用尝试及统计贡献。
- 提供带指定确认文字的“清空全部数据”操作；它会使活动模型请求失效，并删除所有场次和统计数据，但保留 SQLite Schema、后端预设人物目录、静态资源和 `.env`。

## 10. 状态恢复

- 每次合法行动后保存最新快照。
- 扑克 `stateVersion` 只随权威扑克状态变化递增；独立的场次 `eventSeq` 排序所有已持久化的扑克和 Agent 运行事件。
- 扑克状态保持 `inHand`，独立的 `agentRunState` 表示 `idle`、`thinking` 或 `paused`；Agent 暂停和重试不递增扑克 `stateVersion`。
- 页面刷新、浏览器关闭或服务重启后，可以继续未完成场次。
- 正在等待但尚未成功提交的模型结果不会被重复采用。
- 服务重启后，原来处于 `thinking` 的 AI 行动使旧请求失效，并以新的请求标识自动从 DeepSeek 重新开始；原来已经 `paused` 的行动保持暂停，等待人工重试。
- 浏览器刷新或 SSE 重连不取消服务端仍有效的模型请求。
- SSE 断开时前端暂停新行动；重连时通过 `Last-Event-ID` 补发遗漏事件，并读取由私有扑克状态与会话协调状态组合生成、包含当前 `agentRunState` 的最新 `PublicSessionSnapshot`。
- 对外 HTTP/SSE 协议使用 `protocolVersion`，私有扑克快照使用独立的 `snapshotSchemaVersion`，私有事件负载使用 `eventSchemaVersion`；三者与 Drizzle 数据库迁移版本互相独立，不得混用或跨体系比较。
- 私有快照和事件负载恢复时必须经过服务端私有 Zod Schema 校验和显式版本迁移；未知版本或损坏数据进入只读错误状态，不得重新发牌覆盖。

## 11. 非功能需求

### 11.1 正确性

- 服务端是唯一权威牌局状态。
- TanStack Query 是服务端资源在前端的唯一缓存；不得把牌局快照、预设人物、历史或统计复制到 Zustand。
- Zustand 不负责请求服务端、持久化服务端实体或计算扑克规则。
- 所有扑克状态变化必须经过同一个确定性牌局引擎。
- 玩家命令和 AI 命令使用相同的合法性校验和事务提交路径。
- 所有修改场次状态的命令写入持久化命令账本；相同标识和相同负载返回原结果，相同标识和不同负载返回冲突，服务重启后也不能造成重复行动或重复扣款。

### 11.2 性能

- 排除外部模型等待后，普通本地行动应在 200ms 内完成持久化并产生 SSE 更新。
- AI 等待期间界面保持响应。
- Agent 上下文大小不得随场次手数线性增长。

### 11.3 安全与隐私

- 服务仅监听本机。
- 不实施账号与认证。
- API Key 仅存在于后端环境变量。
- 任何日志、错误和前端响应都必须对敏感字段脱敏。

### 11.4 可诊断性

- 每个命令、事件、快照和模型调用具有可关联标识。
- 错误使用中文描述，并给出明确的下一步操作。
- 数据库事务失败时不得出现事件与快照部分写入。

## 12. 验收标准

首版验收必须证明：

1. 可以读取至少八个后端预设人物、选择 5–8 个不同人物、沿用符合当前人数限制的上一场阵容并组建 6–9 人桌。
2. 可以连续完成多手标准无限注德州。
3. 下注、累计不足额全下、短盲、未跟注返还、一次性发完剩余公共牌并逐街 burn、边池、平分以及 6–9 人位置和行动顺序正确。
4. 玩家刷新页面、SSE 重连或服务重启后可以按 `stateVersion`、`eventSeq` 和 `agentRunState` 恢复。
5. DeepSeek 正常决策、DeepSeek→Kimi 条件降级、非法响应纠错和最终暂停均可验证。
6. 不同 Agent 之间没有隐藏信息或记忆串线。
7. 每手可以查看分街日志、全部结果和关联调用链。
8. 用户与 AI 的基础统计符合固定分子、分母和净盈亏口径。
9. 命令账本可以阻止服务重启前后的重复行动和重复补码。
10. 删除整场或清空全部数据后，约定范围内的关联记录和统计贡献同步消失。
11. 360–430px 手机竖屏牌桌、底部安全区域、右侧工具栏和全屏手牌流程可用；宽屏只承载居中的手机画布。
12. 用户可以对任意已结束内部手牌手动请求 Coach 复盘；每个用户决策恰好生成一条包含策略基准、局面约束、对手证据和事后解释的结构化报告。
13. Coach 的当时信息评价与事后事实通过两个模型阶段隔离；未覆盖策略、非 100BB 参考和样本不足均被明确标注，复盘失败或重试不改变牌局状态。
14. 所有 Coach 展示和数据中，动作执行频率与下注尺度不存在歧义；手机端逐街报告和可选范围矩阵可阅读。
15. Player 的 Observation、DecisionPacket 和 Model Adapter 三道信息防火墙均通过泄露回归；Coach 的决策阶段、事后阶段和 Model Adapter 三道边界均通过隔离回归。
16. AgentRun 使用 OwnerScope、预算、版本快照、租约和 fencing；stale Player 运行不能提交，仍需 AI 行动时由当前权威状态重建新运行且不自动弃牌。
17. Coach 每次重新执行生成新的 `coachReviewId`；每个复盘内以 `(coachReviewId, decisionId)` 唯一保存逐决策冻结 assessment，历史不覆盖。

## 13. 首版明确不做

- 真人联机、账号系统、云同步和公网部署。
- 独立宽屏桌面、平板和横屏牌桌布局。
- 2–5 人桌及单挑模式。
- 锦标赛、前注、straddle、抽水及其他扑克变体。
- 求解器、胜率/EV 最优解和高级范围编辑器。
- 实时 Coach、每手自动复盘和 Coach 代打。
- 外部 Hand History 导入、自由理论问答和多意图 Coach 聊天。
- 长期打法标签、情绪识别和用户漏洞画像。
- 动画式牌局重放。
- 数据导入或导出。
- 多语言和音效。
- AI 自由聊天、后台自主工具调用或角色间通信。
- 通用 RAG、动态 Skills/Plugins、Agent 自主 Cron 和协作式 Multi-Agent。
- 真实认证、计费、PostgreSQL、外部消息队列和分布式 Worker；这些只保留替换边界。
- 本地机器人或规则策略代打。
- 用户创建、编辑、复制、删除或导入 AI 人物。
