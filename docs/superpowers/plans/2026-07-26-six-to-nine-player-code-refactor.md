## 1. 修改背景

产品原先支持 2–6 人桌，即一个本地用户加 1–5 个 AI。新需求把场次人数限定为 6–9 人，即：

- 一个固定本地用户。
- 5–8 个 AI。
- 首版不再创建或继续 2–5 人场次，也不再实现单挑特殊规则。
- 同一场次仍禁止重复选择同一个预设人物。
- 为支持九人桌的八个不同 AI，预设人物目录从六个扩展为八个。

盲注 10/20、每席初始筹码 2,000、连续现金桌、AI 自动买入、牌局日志、供应商路由、状态恢复和数据权威边界均不改变。

## 2. 已确认的领域边界

### 2.1 座位与人数

- 座位号范围从 `0..5` 扩展为 `0..8`。
- 创建场次必须选择 5–8 个不同 `personaId`。
- 用户与 AI 的座位总数必须为 6–9，所有座位号唯一。
- `PublicSessionSnapshot.seats` 必须包含 6–9 个座位。

归档后新增的“本地用户固定领域座位 `0`、AI 只能使用 `1..8`、服务端安全随机首手按钮”规则不属于这次历史返工，已由人物目录设计、后端设计、M1.1 设计和主开发任务接管。

### 2.2 逻辑位置

每手发牌时固化下列位置：

- 九人桌：UTG、UTG+1、MP、LJ、HJ、CO、BTN、SB、BB。
- 八人桌：UTG、MP、LJ、HJ、CO、BTN、SB、BB。
- 七人桌：UTG、LJ、HJ、CO、BTN、SB、BB。
- 六人桌：UTG、HJ、CO、BTN、SB、BB。

按钮仍按有效座位顺时针轮转；小盲为按钮左侧第一个有效座位，大盲为再下一个有效座位。翻前从大盲左侧第一个有效座位开始，翻后从按钮左侧第一个仍在手牌中的座位开始。

### 2.3 新增预设人物

新增人物均使用 `personaVersion = 1`：

| personaId | 名称 | 头像色 | tightness | aggression | bluffTendency | pressureCallTendency | riskPreference |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| `small_ball_reg` | 小球常客 | `#0E7490` | 55 | 55 | 35 | 55 | 30 |
| `trap_specialist` | 慢打猎手 | `#BE185D` | 75 | 40 | 20 | 60 | 40 |

公开摘要：

- 小球常客：使用较小尺度和频繁位置施压，适合练习底池控制与反制小尺度。
- 慢打猎手：前段克制、强牌延迟发力，适合练习识别慢打和延迟进攻。

改造当时使用 `docs/ai_poker_persona_design.md` 作为创意来源。当前八个人物 V1 的完整公开字段以 [人物目录设计 §2](../specs/2026-07-24-persona-catalog-m0-design.md) 为唯一规范事实源；首版仍不向浏览器暴露 Prompt、范围表或完整模型配置。

## 3. 改造前代码基线与已完成返工

改造启动时，仓库只在 M0 层实现了旧人数上限和六个人物目录；牌局引擎、会话服务、数据库 Schema 和正式牌桌 UI 尚未实现。因此当时没有 SQLite 数据迁移或历史兼容负担。以下条目记录已经完成的历史修改，不是当前待办。

### 3.1 `packages/contracts/src/index.ts`

当时的修改项（已完成）：

1. `SeatNumberSchema`
   - 当前：整数 `0..5`。
   - 目标：整数 `0..8`。
2. `AGENT_PERSONA_IDS`
   - 追加 `small_ball_reg` 和 `trap_specialist`。
   - 保持列表顺序与服务端目录顺序一致。
3. `CreateSessionPersonaSelectionSchema`
   - 当前：数组长度 `1..5`。
   - 目标：数组长度 `5..8`。
   - 继续拒绝重复人物和重复 AI 座位。
4. `PublicSessionSnapshotSchema.seats`
   - 当前：数组长度 `2..6`。
   - 目标：数组长度 `6..9`。
5. 所有复用 `SeatNumberSchema` 的行动者、当前行动位和公开座位字段自动获得 `0..8` 范围，不另建第二套座位 Schema。

改造时项目尚未发布，且不存在需要兼容的正式客户端，因此在首版发布前直接修订了 `protocolVersion = 1`。如果协议未来已经被外部客户端消费，则必须升级 `protocolVersion`，不能静默修改既有版本。

### 3.2 `packages/contracts/test/contracts.test.ts`

保留必要边界测试：

- 恰好 5 个和 8 个不同人物选择成功。
- 0–4 个和 9 个人物选择失败。
- 座位 `0` 与 `8` 成功，`-1` 与 `9` 失败。
- 重复人物和重复座位继续失败。
- 6 席和 9 席公开快照成功，5 席和 10 席失败。
- 新增两个 `personaId` 可以解析，未知人物继续失败。

不要为 5、6、7、8 每个数组长度复制同构用例；只覆盖最小值、最大值和边界外。

### 3.3 Contracts 构建产物

`packages/contracts/dist/index.js` 和 `dist/index.d.ts` 是 TypeScript 构建产物，不应手工编辑。修改源码后通过 Contracts `build` 重新生成，确保 Server 测试读取最新协议。

### 3.4 `apps/server/src/personas/catalog.ts`

当时新增了 `small_ball_reg` 和 `trap_specialist` 两个冻结目录项：

- 标识、名称、头像色和五个风格刻度使用 §2.3 固定值。
- 背景描述与教学摘要必须为非空中文文本。
- 不新增 Prompt、范围表、模型密钥或运行时决策逻辑。
- 私有目录和公开投影继续经过现有 Zod Schema。

### 3.5 `apps/server/test/unit/personas.test.ts`

当时的修改项（已完成）：

- “恰有六个人物”改为“恰有八个人物”。
- 目录标识顺序仍与 `AGENT_PERSONA_IDS` 完全一致。
- 两个新增人物的公开摘要均通过共享 Schema。
- 冻结、敏感字段排除和已知人物查询测试保留，不为每个人物复制相同测试。

## 4. 改造当时尚未实现模块的目标边界

这些模块在改造当时不需要返工代码；其目标随后已转入正式规格与主开发任务。本节只保留历史背景，不作为当前实现清单。

### 4.1 牌局引擎

- 领域状态只接受 6–9 个唯一座位。
- 发牌支持 6、7、8、9 人各两张底牌。
- 按 §2.2 固化逻辑位置。
- 不实现 2–5 人和单挑 BTN/SB 特例。
- 单元测试覆盖四种人数的按钮、庄盲、首个行动位和跨手轮转。
- 属性测试生成器的座位数量范围改为 6–9。

### 4.2 SQLite 与恢复

- 所有座位列和私有快照座位号允许 `0..8`。
- 场次快照和 `session_agents` 必须有 6–9 个唯一座位。
- 不需要为本次变更新增人物表，人物仍在创建场次时固化到 `session_agents`。
- 当前尚无生产 Schema 或历史数据库，因此不需要迁移旧 2–6 人场次；如果实现前出现旧数据，旧场次应保持只读而不是伪造额外座位。

### 4.3 会话服务与 API

- 创建场次只接受 5–8 个不同人物。
- 拒绝人数越界、未知人物、重复人物、重复座位、座位号越界及与用户座位冲突。
- “沿用上一场阵容”只能沿用已经满足 6–9 人限制的阵容。
- 所有座位仍以 2,000 筹码开始。

### 4.4 Agent Harness

- 九人桌中最多同时存在八个独立 Agent 配置和记忆槽位。
- 观察构建器必须对八个 AI 分别执行隐藏信息白名单。
- 有界记忆在八个对手统计槽位存在时仍遵守 16KB 上限。
- 不改变单回合决策、DeepSeek→Kimi 路由或暂停规则。

### 4.5 历史与统计

- 保存并筛选 UTG+1、MP、LJ 等新增逻辑位置。
- 分街行动顺序适配九人桌更长的行动序列。
- 统计公式和分子/分母口径不改变，只扩大位置维度的枚举。

### 4.6 手机牌桌

- 牌桌拥有九个固定视觉锚点：用户在底部中央；AI 位于顶部左右各一席、左右两侧各三席。
- 6、7、8 人桌按对称规则隐藏空位。
- 右侧工具栏不能与右侧三个 AI 座位重叠；短屏时折叠为单一工具入口。
- 在 360px、390px、430px 宽度分别人工验证 6、7、8、9 人布局。
- 座位信息过密时优先保留头像、筹码、逻辑位置和行动状态，详细人物信息仍进入 AI 状态页。

## 5. 当时采用的修改顺序

1. 修改 Contracts 源码与契约测试。
2. 重新构建 Contracts 产物。
3. 扩展服务端人物目录与人物单元测试。
4. 运行当前完整验证，恢复 M0 绿色基线。
5. 后续按 M1–M7 任务直接实现 6–9 人目标，不再实现旧的 2–6 人分支。

## 6. 当时的验证闭环

返工完成时运行：

- `pnpm run test:contracts`
- `pnpm --filter @poker-practice/contracts run build`
- `pnpm run test:server:unit`
- `pnpm run typecheck`
- `pnpm run verify`

完成标准：

1. Contracts 接受且只接受 5–8 个 AI、6–9 个总座位和 `0..8` 座位号。
2. 服务端目录恰有八个唯一人物，公开投影不泄露私有字段。
3. 返工完成时的 M0 测试、类型检查和格式检查全部通过。
4. `apps` 与 `packages` 下不存在未经本任务授权的其他行为修改。
