## 1. 目标与范围

补齐 M0.2 要求的预设人物公开协议，并在服务端源码中固化首版八个只读、版本化人物，以满足九人桌选择八个不同 AI 的上限。前端未来只读取公开摘要并提交 `personaId` 选择；服务端在 M2 创建场次时复制完整人物快照，M4 再把该快照用于 Agent 上下文。

本次不实现人物 API、数据库表、组桌界面、GTO/策略引擎、教练功能、范围表、量化下注频率、漏洞标签或 Prompt 片段。`docs/ai_poker_persona_design.md` 仅作为首版人物名称、风格和教学文案的创意来源；最终公开字段以本文 §2 的规范表为准，其超出已确认产品范围的策略架构不进入本次实现。

## 3. 对外共享协议

`packages/contracts` 只提供严格的公开 Schema：

- `AgentPersonaIdSchema`：稳定的预设人物标识。
- `AgentPersonaSummarySchema`：标识、版本、姓名、头像色、背景描述、教学摘要和五个风格刻度。
- `AiSeatNumberSchema`：创建场次时 AI 可使用的领域座位号，严格限制为整数 `1..8`；通用 `SeatNumberSchema` 仍为 `0..8`。
- `SessionPersonaSelectionSchema`：创建场次时的一个人物标识和 `AiSeatNumberSchema`。
- `CreateSessionPersonaSelectionSchema`：5–8 个选择，人物标识和 AI 座位均不得重复。请求不携带 `userSeatNumber`，本地用户领域座位隐式固定为 `0`。
- `PersonaSnapshotFilterSchema`：按人物标识及可选版本筛选历史配置快照。

共享协议不得包含范围表、行动频率、漏洞标签、内部策略说明、Prompt、模型密钥、模型标识、路由或模型参数。人物目录中不存在用户写入操作的 Schema，也不存在“模型配置摘要”字段。

DeepSeek 是否满足开场条件、Kimi 是否可用于降级以及连接检测结果不属于人物，由 [后端设计 §13.1](./2026-07-23-poker-practice-backend-design.md) 定义的独立 Provider Settings/Health 共享协议提供。其四态检测摘要只作诊断，开场与降级资格只由对应 Key 是否配置决定；前端不得根据人物目录推断供应商状态。

## 4. 服务端边界

新增的服务端人物目录是版本控制的只读产品配置，而不是运行时数据库事实源。目录定义由服务端私有 Zod Schema 校验，并从同一份私有定义生成公开 `AgentPersonaSummary`。目录查找和版本校验留给后续 M2/M3 服务层；本次仅提供可导入、可测试的只读目录，不引入 `supabase-js` 或任何浏览器数据库访问。

M2.3 已通过服务端 Repository 把人物完整配置快照固化到 `app_private`，并把私有策略说明和人物模型配置纳入版本化目录；Prompt、路由、重试和 Runtime 行为仍由 M4 扩展。这些私有字段不得进入 `AgentPersonaSummary`，也不得回写、改变或重新解释历史快照。历史快照是运行事实，源码目录仍是新场次可选人物及版本的规范源。

## 5. 验证

- 共享 Schema 解析代表性人物摘要、选择与筛选条件，并拒绝重复人物、重复座位、越界人数和敏感额外字段。
- 创建选择接受 AI 座位 `1` 和 `8`，拒绝 `0`、负数和 `9`；公开场次快照必须恰有一个位于座位 `0` 的本地用户，其余座位均为 `1..8` 的 AI。
- 服务端目录恰有八个唯一人物标识，版本稳定，所有公开投影均通过共享 Schema。
- 测试逐字段断言版本 1 的八个人物公开投影与 §2 规范表一致，避免公开字段被原地改写而未提升版本。
- 测试断言公开投影不包含 Prompt、范围表、模型标识、模型参数、路由、模型配置或密钥；不调用模型、数据库或网络。
- 运行 Contracts 测试、Server unit 测试、类型检查和完整 `verify`。
